# Wardrobe security review

Reviewed 2026-10-01. Scope: preserved web/backend source, mobile security boundaries, and the read-only workspace dependency audit. This document records findings and proposed follow-up work. It does not authorize provider activation, deployment, credential changes, database migrations, or broad security refactoring.

## Release assessment

The monorepo and native bundle can compile while the existing production application still has security defects. Build success does not resolve the payment, personal-data, authentication, or dependency findings below. Release should remain gated on payment callback authentication/consistency, reviewer privacy, verified-phone changes, Telegram order binding, and applicable critical dependency advisories. None of these legacy business flows was rewritten during this review.

The source contains real protections: customer cart/order rows are owner-scoped, admin order/payment controls use role guards, Telegram receipt approval checks the configured admin account, login checks password/active/verified state, and JWT validation checks the current active user. Those protections do not cover the separate weak paths identified here.

## Evidence and limits

- The review read application source and manifests. Production configuration, reverse-proxy restrictions, actual public endpoint reachability, database contents, and exploitation were not verified.
- No production service was started, database migrated, SMS/email sent, bot launched, receipt submitted, payment initiated, or provider callback exercised. Statements about impact are source-based assessments with explicit prerequisites, not claims of an observed live incident.
- Mocked mobile transport/session tests and isolated local GraphQL contract tests are separate validation artifacts. They do not constitute a provider certification or a production penetration test.
- File references below use paths relative to the repository root; the number after a colon is the inspected source line. No secret values, payment credentials, OTPs, private tokens, or private keys are included.

## Critical findings

### C1 — Payment callback authentication can fail open

Evidence: `apps/server/src/modules/payment/providers/click.provider.ts:38` and `:40`; `providers/payme.provider.ts:32` and `:34`. Both verification functions return true if test mode is enabled **or the configured secret is absent**. `payment.controller.ts:40`/`:64` then accept those verifications and can call `markPaid` or `markFailed`.

Impact prerequisite: callback routes are reachable and the relevant test flag is enabled or secret is missing. An unauthenticated caller knowing a valid initialized payment/order identifier could change payment state without provider authorization. Turning off the test flag alone does not correct the missing-secret branch. The global rate limiter does not authenticate a callback.

Release gate: fail closed on missing production credentials; isolate test endpoints; verify provider signature/authentication, merchant, amount, transaction/order state, and callback replay rules in a dedicated payment change. Compatibility risk: existing credential-free local tests and any deployment relying on implicit fallback will stop working; document a deliberately isolated fake-provider path before removing fallback behavior.

## Low findings and maintenance risks

- GraphQL playground is always enabled (`apps/server/src/app.module.ts:62`); no explicit production introspection restriction appears in the inspected configuration. This is discoverability/hardening, not authorization. Decide a production policy after preserving internal tooling needs.
- Next build skips TypeScript/ESLint errors (`apps/web/next.config.js:28`/`:29`). Standalone checking is necessary for the release gate; a successful Next build alone is insufficient. Tightening this gate can expose old warnings and should be reviewed independently of relocation.
- Anonymous presence stores arbitrary clientId keys in memory (`apps/server/src/modules/presence/presence.controller.ts`, `presence.service.ts:29`) and cleans them when count is read. Bound identifier size/entry lifetime if this remains public; the counter is untrusted display data and must not drive authorization.
- Product/cart acceptance is not stock reservation, and existing cart quantity updates can exceed stock until checkout revalidates. Preserve server-authoritative checkout behavior; UI estimates must not promise reservation or guarantee payment acceptance.

## Mobile boundaries already implemented

- Access/refresh token pair is one atomic SecureStore record using WHEN_UNLOCKED_THIS_DEVICE_ONLY; no tokens enter AsyncStorage, public preferences, example env files, source constants, form persistence, diagnostics or shared-package configuration.
- Secure writes/deletes are serialized and tied to a session generation. Account replacement/logout invalidates private queries/cache and prevents a late refresh/private retry from acting under another account.
- Public login/register/reset do not attempt authenticated refresh. Focus/session guards reject late successful auth/OTP responses after navigation/account replacement. Fourteen mocked native-storage/auth tests cover offline/idempotent hydration, redaction, stale login/refresh, logout races and cache clearing; no real native store or backend is used by those tests.
- Email reset links accept one 64-character hex token matching the existing backend randomBytes(32) contract; malformed/repeated parameters are rejected, never rendered/logged/persisted. Tokens are not carried as login continuations.
- Login continuations accept only known internal routes, bounded validated product/order identifiers and allowed checkout/payment-return selection fields. Payment return selects the authenticated owner's order through the API; URL fields never mark an order paid.
- Native checkout preserves server totals and the existing manual transfer/Telegram receipt workflow. It does not call initiatePayment, webhook/test-checkout routes, emulate receipt approval, or claim a deep-link success query proves payment.
- Phone editing/account deletion/native photo upload are not fabricated through unsafe or admin endpoints. Unsupported deletion directs the user to configured support; a production release still requires a real approved account-deletion policy/contract and platform compliance review.
- API URL is explicit; release URLs require HTTPS. Native shared configuration contains public values only. Live API/payment/SMS/provider verification remains a separate release task.

## Safe remediation order

1. Confirm deployment reachability, proxy topology, production OS and provider feature flags through an authorized read-only server inventory. Record names/booleans only; do not expose secrets. The current review cannot assume production is already protected.
2. Build a scoped dependency patch proposal using the full advisory report and official compatible version ranges. Show precise version/peer changes and required validation before installation; do not upgrade merely to newest and do not run broad audit fixes.
3. Review payment fail-closed authentication, amount/provider/ownership/idempotency and the single inventory transition together. Use an isolated database and provider sandbox, never production callbacks, for validation. Preserve manual Telegram support/payment modules throughout.
4. Correct public reviewer privacy and verified-phone changes with explicit API compatibility notes and focused authorization tests. Replace raw Telegram order binding with an owner-authorized expiring token flow.
5. Harden secret logging, OTP randomness/attempts and refresh revocation without losing legacy verification/recovery access. Add upload HTTP guard/content tests, query limits, CORS and safe error reporting as small separate changes.
6. Only after those scoped gates and isolated integration checks, perform an approved release review covering real payment reconciliation, domain links, device QA, account deletion, push credentials/permissions and rollback. The current monorepo validation does not authorize a production cutover.

# Validation pipeline

`.github/workflows/validate.yml` runs on pull requests or manual dispatch. It has read-only repository permission and no deployment credentials. It pins pnpm 10.33.4 and Node 22.15.1, installs the frozen lockfile without lifecycle scripts, builds shared packages, generates Prisma, checks application types, runs unit tests, builds Next/Nest, exports Android/iOS JavaScript bundles, checks the Turbo graph, and exercises the API against a newly created isolated SQLite database. No production migration, bot process, payment provider, or external messaging is part of this pipeline.

Existing workspace packages are small, so the first pipeline validates the whole repository. Turbo already orders shared builds before applications. Add change filtering only after reliable baseline runs, always invalidating dependent applications when shared packages or the lockfile change. Hosted Linux execution has not been observed from this local Windows session; the workflow must receive its first real pull-request run before it is relied on.

The workflow pins immutable action commits resolved read-only from the official v7 checkout/setup-node and v6 pnpm/action-setup release tags on 2026-10-01. Before enabling it on an organization repository, review those releases and the organization's runner policy. References: [checkout](https://github.com/actions/checkout), [setup-node](https://github.com/actions/setup-node), [pnpm/action-setup](https://github.com/pnpm/action-setup). GitHub's action runtime is independent of the project's Node version.

Production deployment should be a separate approved workflow with reviewed persistent mounts, backups, smoke tests, traffic switching and rollback. Mobile EAS development/preview/production builds should be another manually approved workflow using a verified Expo project and protected signing access. Store submission remains a separate human decision. Do not attach production secrets to untrusted pull requests.
